# Languages, and which way the page runs

## The locale is a property of a person, not of the URL

The App Router's usual answer is a `[locale]` route segment, and for a public
site it is the right one: a search engine has to index the Hindi page
separately, and a shared link has to open in the language it was read in.

**Neither is true here.** Every screen is behind a login, nothing is indexed,
and a link sent from one member of staff to another should open in *the
reader's* language rather than the sender's. So the locale is resolved
server-side exactly as the tenant and the session already are, and `/students`
stays `/students` in every language — no route restructure, no duplicated
sitemap, no `/hi/` prefix to strip in forty `redirect()` calls.

The cost, stated rather than discovered: **there is no per-locale caching by
URL**, so a shared cache in front of this app would have to vary on the cookie.
Nothing in this deployment does that today.

### The resolution order

| | Source | Why it is here |
|---|---|---|
| 1 | `user_profiles.locale` | what this person chose, on any device |
| 2 | the `schoolos-locale` cookie | what they chose **before signing in** |
| 3 | `Accept-Language` | what the browser asked for |
| 4 | `tenants.default_locale` | what the school runs in |
| 5 | `en` | |

Step 2 is the one that is easy to leave out and expensive to miss: somebody who
cannot read the default language has no profile yet, so the cookie is the only
place their choice can live while they are looking at the login page.

`user_profiles.locale` being **null** means *"follow the school"*, which is
deliberately not the same as having chosen the school's current language. If the
school switches to Hindi, the person who never expressed a preference switches
with it and the person who explicitly chose English does not.

## Two halves that must not drift

`reference.locales` says which languages a **deployment** offers.
`LOCALES` in `src/lib/i18n/config.ts` says which ones this **build** has
messages for. That is the same split as `CHANNELS[].driver` against
`notification_channel_settings`: a row in a table cannot know whether a
catalogue was written, and a constant compiled into the bundle cannot know
whether a school switched a language off.

`localeCoverage()` is what keeps them honest, and it is
`grading_scheme_problems()` applied to a message catalogue.

### Why a translation is allowed to be incomplete

English is the source catalogue and its keys are the contract; every other
locale is typed as `Partial<Record<MessageKey, string>>`. That makes an
incomplete translation **representable** rather than a compile error — and that
is the whole design:

> A catalogue that must be complete to compile is a catalogue nobody adds a
> language to. A catalogue that may be incomplete *and says how incomplete* is
> one somebody can finish over three afternoons.

At runtime the fallback is **silent**, because a parent is better served by an
English sentence than by a raw key or a blank. So the honesty lives elsewhere:

- `coverageProblems()` returns sentences, rendered on `/settings/language`.
- `tests/i18n/i18n.test.ts` holds a **floor** per locale. Raise it when a
  translation is finished; **never lower it** — a dropped key is the only way it
  can fail, and lowering the number to make it pass is deleting somebody's work
  and calling it a fix.
- The floor is 95 rather than 100 on purpose: a few English keys may land ahead
  of their translations without stopping the build. All three locales sit at
  100 today.

A key with **no English either** is a programming mistake, not a translation
gap, so `t()` renders the key itself — the loudest thing that is still safe on
somebody's screen.

## Right to left is a requirement, not a setting

Urdu is in the list precisely so that RTL is exercised rather than declared.
**RTL that nothing uses is RTL that is broken and nobody has noticed**, and a
test asserts at least one locale runs right to left.

### Layout: logical properties, applied mechanically

Every physical Tailwind utility became its logical twin across 60 files and 349
lines:

| was | is |
|---|---|
| `ml-` `mr-` | `ms-` `me-` |
| `pl-` `pr-` | `ps-` `pe-` |
| `text-left` `text-right` | `text-start` `text-end` |
| `border-l` `border-r` | `border-s` `border-e` |
| `rounded-l` `rounded-r` | `rounded-s` `rounded-e` |
| `left-` `right-` | `start-` `end-` |

Each is an **exact equivalent in LTR**, so the left-to-right rendering is
unchanged and the change is verifiable by the build alone. The codemod anchored
every pattern on a class-name boundary so `rounded-lg` was never mistaken for
`rounded-l`; the two places it still reached into English prose (`right-aligned`
in a comment) were put back by hand, and negative margins needed a second pass
because `-ml-3` does not start at a boundary.

`dir` goes on `<html>`, not on a wrapper. Scrollbar placement, the direction a
`<select>` drops in, and every logical utility all read it from the document
element.

### Icons: the part that cannot be mechanical

An arrow meaning "back" points the other way in Urdu; an arrow meaning
"download" does not. lucide-react puts the icon's own name in a class, so the
directional ones are flipped by name in `globals.css` — a heuristic,
deliberately narrow, and easier to audit than an `rtl:rotate-180` scattered
across thirty call sites.

Three more things turn around: the mobile navigation drawer comes in from the
side the reader starts on, the collapsed-sidebar tooltip appears on the side
being read *away* from (otherwise it covers the label it explains), and the
toast rail moves to the top-left — a message that appears in the corner your eye
does not start from is a message you find after it has gone.

Numbers get `unicode-bidi: isolate` inside RTL. The bidirectional algorithm
mostly handles them; it does not when a number is followed by punctuation, which
is exactly the shape of a receipt number, a percentage and a time.

## Formatting

The codebase was full of `toLocaleDateString("en-IN")` — correct for one school
and wrong the moment somebody reads the same screen in Urdu. `format.ts` routes
dates, times, numbers and money through `Intl` with the reader's locale.

**Currency is not localised away from INR.** The rupee is a fact about the
money, not about the reader: a fee of ₹18,900 is ₹18,900 in every language, and
only the digit grouping and the symbol's placement move. `intlTag()` returns an
Indian tag for every locale for the same reason — the reader's language changes,
the school's conventions do not.

Every formatter returns `—` for a missing value and never `0`. The difference
between "not entered" and "zero" is load-bearing everywhere else in this
codebase and it does not stop being load-bearing here.

## Writing a translatable screen

```tsx
// Server Component
const t = await getT();
<h1>{t("settings.language.title")}</h1>

// Client Component
const t = useT();
<Button>{t("common.save")}</Button>

// counts
{t.plural("channels.waitingCount", queued)}
```

Keys are flat and dotted (`area.thing`), interpolation is `{name}`, and a
plural has `.one` / `.other` siblings read through `t.plural` — `Intl.PluralRules`
picks the category, so a language with more than two can be added without
touching a call site. A test checks that every `.one` has a matching `.other`,
because a missing `.other` renders as a raw key for every count except one, and
that only shows up on the second row of a table.

A placeholder with nothing to fill it is left as `{name}` rather than rendered
as `undefined`: a stray `{name}` on screen is a bug report, and "Hello
undefined" is a bug somebody laughs at and does not report.

## The office batch, and what it cost

The four label batches before this one took the screens a family reaches. This
one takes the rest — the admissions funnel, the rollover, the schedule register,
the audit trail — and finishes the set: **`STILL_ENGLISH` is 0.**

Eleven helpers gained a `Translator`. The twelfth, `audit.fieldLabel`, did not,
and the distinction is worth keeping:

> `WEEKDAYS` was deleted because **`Intl` already knew the answer**.
> `fieldLabel` stays because **there is no answer to ask for**: its input is an
> arbitrary Postgres column name from any of a hundred tables — an identifier,
> not a value this product chose from a list — so there is no finite set of
> words to catalogue. It is named in `NOT_A_LABEL` with that reason rather than
> counted.

### Three things it found on the way past

- **A second hardcoded weekday array.** `DAY_NAME` sat in `schedules.ts`, doing
  exactly what `WEEKDAYS.label` was deleted for one batch earlier. **When you
  delete a hardcoded table, grep for the second one.** The cadence sentence now
  asks `formatWeekday`, and joins with `Intl.ListFormat` so the conjunction and
  the separator are the reader's too — "Monday, Tuesday and Friday" against
  "सोमवार, मंगलवार और शुक्रवार". Hand-joining with `" and "` was the same
  mistake one clause along.

- **`decisionLabel(d).toLowerCase()`, still at two call sites.** Rule 15 already
  names this — Hindi and Urdu have no letter case, so it is a no-op in every
  locale except the one it was written for. It survived the sweep that found the
  other two **because this module's label was still English, so the call was
  still doing something.** A dead-looking fix can only be seen from the locale it
  is broken in. `currentlySentence` and `tallySentence` are keys now: the
  sentence is the unit, not the word.

- **Hindi has five `Intl` ordinal categories, not one — and the fallback turned
  a missing key into a wrong sentence.** The first draft assumed `hi` and `ur`
  both return `other` for every number. Measured: Urdu does; **Hindi returns
  one/two/few/many/other**, because its ordinals are distinct words (पहला,
  दूसरा, तीसरा, चौथा, छठा) rather than suffixes. The four missing keys fell
  through to English — and the English entry is not a *word* but a *rule*,
  `"{n}st"` — so a Hindi reader was shown **"हर माह की 1st तारीख़ को"**.

  > Silent fallback to English is the right runtime behaviour for a missing
  > **translation** and exactly wrong for a missing **rule**. Where a key holds
  > a locale rule rather than a sentence, **every branch of it must exist in
  > every locale** — and the guard asks `Intl` which branches there are rather
  > than trusting anybody's reading of CLDR.

  `schedules.ordinal.many` is declared in English too, which English never
  selects: English is the *source* catalogue, every other locale is typed as a
  `Partial` of it, and a key existing only in a translation is a stale key by
  `i18n.test.ts` and a type error besides. Urdu carries all five for the mirror
  reason — it selects only `other` today, and the four it does not took its
  coverage to **99.0%**, reporting a gap that was not one. **A branch a locale
  cannot currently select is still a key it must have**, or the next ICU update
  leaks the English rule into that language rather than merely missing a word.

### And a hint is part of the control, not prose beside it

`promotion.decisionHint`, `promotion.onMissingResultHint`, `renewals.blurb` and
`schedules.kindDescription` render *directly beneath* the name their label
helper returns, on the same radio or the same card. Translating the name and
leaving the explanation is one value shown in two languages on one control —
the second-consumer failure the family batch wrote down, arriving where the
hints actually live.

### What it weighs

Built before and after, and **the instrument was checked first**: two builds of
the *same* commit disagree by 1 kB on 3 of 90 routes, so anything under 2 kB is
not a reading.

| | |
|---|---|
| whole client build | **2,288,157 → 2,304,191 bytes, +15.7 kB** for ~80 keys × 3 languages |
| First Load JS | **+2–3 kB on 59 of 90 routes** — the shared catalogue chunk growing |
| unchanged | 17 routes |
| *reported* −1 kB | 14 routes, stable across two baselines |

That last row is reported and **not claimed**: adding keys cannot make a route
smaller, so it is Next redistributing chunk boundaries, not a saving. *A number
that moves in a direction your change cannot produce is measuring something
else* — the same rule the redundant-index pass learned on a timing.

The useful half for whoever does the next batch:

> **A `Translator` reached through `await getT()` costs the browser nothing.**
> Five of this batch's call sites are Server Components — `/checks`,
> `/certificates/[id]`, `/hostel/[hostelId]`, `/transport/[routeId]`,
> `/promotion/renewals/[runId]` — and `/checks` sits at 107 kB before and after,
> `/certificates/[id]` at 143 kB. The 1–2 kB per route is paid only by the
> client components. When a screen can be converted server-side, it is free.

## What is not built

- **The catalogue covers the shell, navigation, common actions, list states,
  the login screen, notification channels and the language screen.** It does
  not cover the body copy of the other forty screens — those are still English
  regardless of locale, which the coverage number does *not* claim otherwise
  about, because the number measures the catalogue and not the application.
  That gap is the honest headline: **the mechanism is complete, the translation
  is not.**
- **No locale in the URL**, per the top of this file — so no per-locale HTTP
  caching.
- **No date-picker or calendar localisation.** The inputs are native, so they
  follow the browser's locale rather than the app's, and those two can disagree.
- **No translated database content.** A subject called "Mathematics" is stored
  once; the school types it in the language it wants it printed in. Per-tenant
  content translation is a bigger idea and is not started.
- **No pseudolocale.** The usual way to find hardcoded strings is a fake locale
  that lengthens everything by 40%; without one, a string that never made it
  into the catalogue is found by reading.
- **Numerals are Latin in every locale.** `hi-IN` and `ur-PK` both default to
  Latin digits in `Intl`, which is what Indian schools use on a fee receipt.
  A school wanting Devanagari or Eastern Arabic numerals would need a rules key.
